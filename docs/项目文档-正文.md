## 第 1 章 · 现状痛点与机会

### 1.1 中小制造企业的真实处境

精密零件产线做视觉质检改造，难点通常不在"能不能拍清楚"——工业相机与光源方案已经相当成熟。
真正卡住的是三件事：

1. **说不清结论怎么来的**。一份改造方案里写着"不良品率可降 35%"，但没人能回答这个数字出自哪份文件、哪一年、什么口径；
2. **不敢用模型写的东西**。大模型能在几分钟内产出一份结构完整的方案，但里面的数字、引用、结论往往没有出处，业务方不敢拿去立项；
3. **看不到失败过程**。多数演示只给最终成功画面，中间改了几轮、哪一轮不合格、为什么回退，全部被剪掉。

### 1.2 我们的判断

把"可核验"做成**交付物的结构**，而不是事后补一段说明：

- 每条结论都能回到原文的字符区间；
- 每轮评分都留档，包括不合格的那几轮；
- 每次失败都留下 trace，而不是被覆盖。

这不是一个"更好用的写作工具"，而是**让多智能体的产出可以被第三方核对**的编排平台。

### 1.3 机会

对客户而言，"可核验"直接对应采购流程里的两个硬需求：**立项要依据、验收要凭证**。
一份能回到原文的方案，比一份写得漂亮但查不到出处的方案更容易过会。

> 【待补 A】行业侧的具体数据（改造投入区间、典型回收期）：建议引用语料中已标注出处的两三条，
> 不要新增查不到来源的百分比。

**本章证据**：`knowledge/corpus/`（17 份转述卡，逐条带许可依据）与 `docs/测试报告.md` 第二节
（检索命中率实测）；合规判定见 `docs/语料来源与合规.md`。

## 第 2 章 · 方案概述

### 2.1 一句话定位

**不是聊天机器人，是把多智能体产出变成可核验交付物的编排平台（Agent Harness）。**

### 2.2 六项能力如何串成一条链

```
需求
 └─ 知识库检索（17 份语料，混合检索）        ← 能力 1
     └─ DAG 编译（11 节点，声明式工作流）      ← 能力 3
         └─ 调度执行（并发/超时/重试/降级）    ← 能力 4
             └─ 六类角色协作（YAML 声明）      ← 能力 2
                 └─ 评分未达标 → 定向回退      ← 能力 5
                     └─ 两层验证 + 一票否决    ← 能力 6
                         └─ 交付包（9 件文件，全部进 manifest）
```

### 2.3 交付物长什么样

每次运行产出 9 件文件，全部登记进 `manifest` 并附 sha256：

| 文件 | 作用 |
| --- | --- |
| `solution.md` | 方案正文 |
| `evidence_chain.json` | 引用了哪些 `source_id` |
| **`evidence_refs.json`** | **每条引用的 文件 / 页码 / 字符区间 / 原文 / 哈希** |
| `scorecard.json` | 评分卡（终轮结论） |
| **`rounds.json`** | **每轮评分，含首轮 fail** |
| `trace.jsonl` | 全链路事件（start/end/revise/fail/retry/degrade） |
| `charts/scorecard.svg` | 评分卡五维柱状图 |
| `charts/convergence.svg` | Self-Loop 收敛曲线（含 0.85 阈值线） |
| `delivery_artifact.json` | 交付清单与上述文件的 sha256 |

### 2.4 与普通 Agent Demo 的三点区别

| 维度 | 常见做法 | 本项目 |
| --- | --- | --- |
| 契约 | 先写代码，接口边写边改 | **11 份 JSON Schema 冻结**（tag `contracts-v1.0`），正反例齐全 |
| 失败 | 剪掉、跳过、重试到成功为止 | **安全中止 + 完整 trace**，绝不交付带病的包 |
| 证据 | 给结论 | 给**可回到原文逐字核对**的引用 |

## 第 3 章 · 技术实现

### 3.1 知识库与证据链

- **17 份语料**逐条登记许可依据、署名要求与哈希；**不含任何第三方原文**（全部为本团队原创转述卡）；
- 切片时跳过 YAML front-matter 与"权利依据"等合规声明段——片段数由 119 降到 **51**，避免"版权/署名"类查询命中样板文字；
- 检索为 BM25 + 向量双路，RRF（k=60）融合，`score` 是融合后的归一化分值，不是单路分数。

**实测**（22 条查询，17 条原文词 + 5 条改述）：

| 组 | 查询数 | hit@8 | hit@1 | MRR |
| --- | --- | --- | --- | --- |
| 原文词 | 17 | 100% | 100% | 1.000 |
| **改述** | 5 | 100% | **40%** | 0.607 |
| 合计 | 22 | **100%** | 86.4% | 0.911 |

> **如实说明**：召回好、排序弱。改述查询的 hit@1 只有 40%，这是当前检索策略的真实短板，
> 不用总体 100% 掩盖。

### 3.2 Agent 团队

- 六类角色：planner / researcher / analyst / writer / verifier / reviewer，全部 YAML 声明；
- 每份声明含职责、工具白名单、只读约束、模型档位、超时重试；
- **改 YAML 不重启即生效**（内容指纹比对热加载）；
- 只读角色不得配置有副作用的工具，由 `check_contracts` 与注册表双重校验。

### 3.3 工作流编排

- `workflows/industry_solution.yaml` 编译为 **11 节点** DAG：plan → retrieve → fanout → (analyze ∥ outline) → write → verify → gate → review → snap，另有 revise 循环边；
- 节点集合被契约约束：评分卡的 `target_node` 必须落在 verify 的合法前驱内，否则 `LoopController` 拒绝回退；
- 支持条件分支、并行 fanout、循环边与子图。

### 3.4 动态调度

- 并发信号量、单节点超时、指数退避重试、失败降级、Token 预算护栏；
- 故障注入可复现：

```bash
python -m src.run --inject-fault timeout --node retrieve
# trace: fail×3 / retry×2 / degrade×7，随后安全中止并保留 trace.jsonl
```

**降级是安全中止，不是"继续交付"**：宁可不出包，也不出一个验证不过的包。

### 3.5 Self-Loop

- 评分低于 0.85 时，生成**定位到具体段落**的修订指令，只回退到 `write` 重跑，其余分支结果保留；
- 最多 3 轮；连续两轮无提升则终止；
- 实测：R0 加权分 **0.95 已高于阈值 0.85**，却因一条 blocker 判 `fail`（一票否决生效），R1 修复后 1.0 pass。

### 3.6 结果验证与反馈

| 层 | 实现 | 状态 |
| --- | --- | --- |
| L1 确定性规则 | 引用真实性 / 数值一致性 / 章节完整性 / Schema，5 条规则 | ✅ |
| L2 独立评审 | 温度与撰写者不同（0.0 vs 0.3），相同则**拒绝启动** | ✅ |
| L3 双路比对 | — | ❌ **未实现**，配置为 `false`，设为 `true` 会报错退出 |

失败样本落 SQLite，支持按规则统计与前后对比；**样本少时只报个案**（实现里有 `sample_note` 自律）。

> 【待补 A】本章需要队长补充商业侧判断；以下为可确认部分与待定项。

### 4.1 客户

年产值 1–10 亿、有质检工位但不具备 AI 团队的中小制造企业。

> **口径说明**：这里的产值区间是**待验证的客户画像假设**，不是实测数据，也没有引用来源。本章属于商业判断，与第三、七章的实测数字分开表述——**不把估计值混进实测值里**。（2026-11-11 按 A 的 review 意见标注）

### 4.2 交付形态

不卖软件许可，卖"**可核验的改造方案**"：方案正文 + 证据链 + 可复现的验证过程。

### 4.3 收费结构（示例，待调研修正）

方案诊断费 + 按工位实施费 + 年度验证服务。

> 【待补 A】三类费用的具体区间与依据。**不要编市场数字**——查不到出处的百分比宁可不写。

### 4.4 客户为什么买"可核验"

他们要向老板、银行、客户证明这笔钱花得值。**证据链就是那份证明**：每条结论能回到原文，
每轮评分都留档，交付包可离线复算。

### 4.5 冷启动路径

先在 1–2 个工位做样板，用 `evidence_refs.json` 作为验收依据——验收标准从"看起来不错"变成"能对上原文"。

## 第 6 章 · 合规边界与已知限制

### 6.1 语料合规

- 17 份**原创转述卡**，不含第三方作品原文、长段引用或图表；
- 每条登记 `legal_basis` / `redistribution` / `attribution`；
- 法律依据：《著作权法》第五条（法律法规、行政文件、单纯事实消息不受保护）；
- **严禁**把语料包传到公开仓库/网盘（第二十四条第六项"不得出版发行"）。

### 6.2 技术边界（如实）

| 项 | 现状 |
| --- | --- |
| L3 双路检索比对 | **未实现**，配置显式 `false`，设为 `true` 会拒绝启动 |
| 检索排序 | 改述查询 hit@1 仅 **40%**，是当前短板 |
| L2 判定 | Mock 模式下是**启发式**（bigram 重合、段落矛盾），接真实模型走同一接口 |
| PDF 页码贯通 | 代码路径已通（有测试），但**未用真实 PDF 验证**；当前 17 份语料为 Markdown，`page` 全为 `null` |
| 语料类型 | 转述卡，非真实行业原始资料 |
| 演示第三轮 | 是**故障注入回放**，不代表普通 API 自然跑三轮 |

> 说明这些不是减分项：**能说清边界，比宣称"全都做了"更经得起追问。**

### 6.3 数据与隐私

- 不采集任何个人信息；产线图片若含可识别人脸，不属于本项目必需数据；
- Mock 模式零凭据运行，不读取任何 API Key；
- 提交材料不含校名、导师姓名、学号。
